# 技术栈横向对比（换技术栈对性能与流畅度的影响）

> 回答一个问题：**如果换成别的技术栈，这款软件的性能和流畅度会更好吗？**
> 结论先行：对本应用（表单 + 表格 + 打印的诊所业务软件），横向迁移的收益远小于成本；
> 流畅度的真实瓶颈在当前栈内即可解决，文档末尾给出可执行清单与量化基线方法。

## 1. 先量化现状（决定要不要换的前提）

本应用的实际负载特征（诊所规模：药材数百味、处方数千张/年）：

| 维度 | 现状（Tauri 2 + WebView2 + React/antd） |
|------|------|
| 安装包体积 | 3.1 MB（便携版 7.5 MB） |
| 冷启动 | 秒级（Rust 原生壳 + 本地 SQLite，无运行时下载） |
| 内存占用 | WebView2 进程组约 100~150 MB |
| 交互帧率 | 表单/表格场景稳定 60fps；列表均有分页（15 行/页），无长列表滚动机 |
| 数据规模上限 | SQLite 单机十万行级无压力，诊所场景绰绰有余 |

**关键判断：本应用是"表单表格型"而非"动画/图形型"负载。**
流畅度瓶颈（若有）只可能出现在：首屏加载（antd 包体）、大表格渲染、主题切换瞬间——
三者都能在当前栈内解决（见 §4），而横向迁移主要改善的是后两者不会出现的场景。

## 2. 候选技术栈横向对比

| 维度 | **Tauri + WebView**（现栈） | Electron | Flutter Desktop | Compose Multiplatform | WinUI 3（原生） | 纯 Rust GUI（egui/iced） |
|------|------|------|------|------|------|------|
| 包体积 | **3 MB** | ~85 MB（捆绑 Chromium） | ~20-40 MB | ~30-50 MB（含 JVM） | ~5-10 MB | ~5-10 MB |
| 冷启动 | **快**（系统 WebView） | 慢（起 Chromium） | 中（Skia 初始化） | 慢（JVM 启动） | **快** | **快** |
| 内存 | 100-150 MB | 150-300 MB | 80-150 MB | 150-250 MB | **60-120 MB** | **40-80 MB** |
| 渲染流畅度上限 | 60fps（DOM 合成） | 60fps（同左） | **120fps（Impeller 自绘）** | 120fps（Skia 自绘） | **原生合成** | **原生（GPU 即时模式）** |
| 中文输入法/字体 | **完美**（系统 WebView） | 完美 | 良好（需配字体） | 良好 | **完美** | 弱（IME 支持参差） |
| 复杂表单/表格组件生态 | **antd 全家桶** | 同左（共享 React 生态） | 需自建或第三方（Material 风） | 有但中文场景弱 | WinUI 控件（表格弱） | **几乎没有**，全自绘 |
| 与现有 Rust 后端关系 | 直接编译进同一进程 | 需 Node 桥或重写 | flutter_rust_bridge | JNI 桥 | 需 IPC 或 C# 重写 | 同语言 |
| 迁移成本 | 0（现栈） | 全前端重写且更重 | **全量重写**（Dart） | **全量重写**（Kotlin） | **全量重写**（C#/XAML） | **全量重写**（即时模式范式） |
| 软著/打印/系统集成 | 成熟 | 成熟 | 一般 | 一般 | 强 | 弱 |

**逐项判词：**

- **Electron**：唯一确定的变化是包体 +27 倍、内存翻倍，性能无任何提升。排除。
- **Flutter / Compose**：自绘引擎的 120fps 上限是真实的，但本软件没有需要 120fps 的场景
  （拖拽画布、复杂动画、视频）。为用不上的流畅度上限支付"全量重写 + 失去 antd 中文
  企业组件生态 + IME/打印/可访问性回归风险"，性价比为负。仅当未来要做
  药材图谱可视化、移动端同等 UI 复用时重新评估（Flutter 的多端复用是唯一亮点）。
- **WinUI 3 / 纯 Rust GUI**：原生流畅度与内存是真实的，但表格/表单生态远弱于 antd，
  等于用"框架性能"换"自研组件的卡顿"。即时模式范式（egui）对几十个表单页是灾难。

## 3. 横向视角下真正值得借鉴的两点

不换栈，但吸收两个"隔壁更流畅"的原因：

1. **自绘引擎流畅的本质是" fewer layers + 合成器友好"** —— 对应到 WebView 栈：
   减少重排范围（内容动画只用 `transform/opacity`）、列表虚拟滚动、避免深层
   再渲染（React Compiler / 细粒度状态）。这些都能拿到大部分收益（见 §4）。
2. **原生壳快在"启动少做事"** —— 对应：首屏只加载看板一个路由的 chunk（已做路由懒加载），
   antd 5.20+ 按需 import 已由打包器处理；可再加骨架屏消除感知等待。

## 4. 当前栈内的流畅度清单（无需换栈）

按性价比排序，全部可独立验证：

1. **React Compiler**（`babel-plugin-react-compiler`，19.x 时代已 stable）：
   自动 memo 化，开处方页（左侧全药材列表 + 明细表格高频联动）是最大受益者；
   替代手工 useMemo/useCallback，构建期开启、可逐页灰度。
2. **antd Table 虚拟滚动**：库存/处方历史已有分页兜底；若未来放开"每页 500 条"，
   启用 `virtual` 属性（antd 5.9+ 内置）即可，半天工作量。
3. **首屏感知**：`index.html` 内联主题色骨架屏（纯 CSS，~1KB），消除 WebView 首绘空白；
   `modulePreload` 已由 Vite 处理。
4. **Tauri 侧**：`windows` 创建参数加 `windowEffects`（若要亚克力背景）属视觉项；
   启动关键路径已优化（迁移与自动备份在后台，不阻塞首帧）。

## 5. 决策规则（何时才值得横向迁移）

满足以下**任一**条件时重新评估 Flutter/WinUI：

- 产品形态出现 60fps 承受不了的交互（拖拽排版处方单、药材图谱编辑器、动画营销页）；
- 需要与 Windows 系统深度集成（原生通知/共享/打印后台服务）且 WebView 路径验证不通；
- 内存成为硬约束（目标 <80MB）且 antd 侧优化已到头。

在那之前，**纵向升级（已做：Tauri 2.11 / React 19.3 / Vite 7.3 / TS 6.0）+
§4 清单就是流畅度的最优路径**。
